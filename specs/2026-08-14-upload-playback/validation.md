# Validation: Phase 2 — Upload + Playback

## Acceptance Criteria
- [ ] A1 — Backend `POST /tracks` (JWT-protected) accepts a multipart audio file + title/artist (album/cover optional), extracts the duration server-side with `music-metadata` (never client-reported), stores the file in the private `audio` bucket and (when given) the cover in the public `covers` bucket, records `audioStorageKey` + `durationMs` on the real `Track` row, and returns 201.
- [ ] A2 — Non-audio files, missing audio file, missing title/artist, oversized files, and non-image covers are rejected with 4xx; unauthenticated uploads are 401.
- [ ] A3 — `GET /tracks` returns only the caller's tracks (owner-scoped), each with a fresh signed `audioUrl` (1h) from the private bucket and the public `coverUrl`; the audio object is NOT retrievable without a signed URL (private bucket).
- [ ] A4 — Client shows the bottom-nav shell (Home / Search / Library); Library renders real DB rows (loading / error+retry / empty / data states), and the upload UI pushes a real file through the real API (dio FormData + progress) and refreshes the list on success.
- [ ] A5 — Playback: tapping a track plays sound from the real stored file; play/pause, prev/next (wrapping), seek (slider), shuffle, and repeat (off/one/all) all work from the mini-player and the Now Playing screen.
- [ ] A6 — Background/lock-screen playback: pressing Home keeps audio playing; the media notification shows title/artist + artwork and controls; the lock screen shows controls; relaunching the app keeps the catalog and playback works again.
- [ ] A7 — Every acceptance criterion above has a passing automated check (unit/widget tests in plan.md Groups 1–4 counts) AND the Group 5 on-device manual walkthrough passes end-to-end with a real audio file (engineering-standards Definition of Done — both halves required).
